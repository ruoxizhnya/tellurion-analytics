# 0002 · 报告不可变由 PG 触发器兜底

- **状态**：已裁决（2026-10-24，QT-43 施工 ②）
- **场景**：`analysis.reports` 的 `completed` 是终态：同键重复提交必须返回**字节一致**的已存报告，不能重算、不能覆盖（`docs/dataflow.md` §4 不变量 1）。`Memory` 实现里这是 Go 代码的判断；接 PG 后如果只靠应用层，任何直连 SQL、迁移脚本或未来的写入方都能悄悄改掉一份已出的报告——而报告是复盘依据，改掉就不可追溯。
- **决策**：
  1. `PG.PutReport` 保留应用层语义：已存在且 `status='completed'` ⇒ 同键同内容 no-op、异内容 `ErrReportConflict`；`pending/running` 可推进到终态。
  2. 数据库层加 `BEFORE UPDATE` 触发器 `reports_completed_immutable`：`OLD.status='completed'` 时 `RAISE EXCEPTION`（SQLSTATE 55000）。绕过应用层的直接 `UPDATE` 也会被拒。
  3. 不拦 `DELETE` / `TRUNCATE`：触发器只守「报告内容被改写」这条不变量；清理与运维动作不在本 ADR 范围内（且 `TRUNCATE` 本就绕过行触发器）。
  4. `CHAR(64)` 列读取用 `rtrim`，避免 PG 的空格填充污染哈希比较。
- **理由**：应用层判断容易被绕过，DB 触发器是最后一个不依赖调用方自觉的守卫；它只加在一次 `UPDATE` 上，没有额外表、没有额外版本机制，与现有「启动时跑幂等 DDL」的取向一致。
- **代价 / 后果**：① 修改 `analysis.reports` 的 DDL 时要同步维护函数与触发器（`CREATE OR REPLACE` + `DROP TRIGGER IF EXISTS` 保证可重入）；② 想「修一份已完成的错误报告」只能新增一条记录（新 `report_id` / 新 `metrics_version`），不能原地改——这是有意的；③ 触发器只在本仓 schema 内，不约束其他 schema。
- **替代关系**：无（0001 讲「纯函数只读」，本条讲「PG 上的终态不可变」）
